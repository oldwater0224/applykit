## 2. 목표와 범위

### 목표
네이버 뉴스 검색 API로 국내 스타트업 투자·창업 기사를 매일 수집·정제·저장하고, 홈 화면에서 조회 가능한 데이터 소스를 만든다.

### 범위 (IN)
네이버 API 클라이언트 / 관련성 필터 / 중복 제거 / DB 저장 / 크론 연동 / 조회 API·서버 액션 / 수동 실행 라우트 / 캐시 무효화 / 단위 테스트 / 데이터 보관 정책

### 범위 밖 (OUT)
- **UI·디자인 구현 일체.** 조회 함수는 순수 데이터만 반환하고 표현 형식(날짜 포맷, 금액 단위, 말줄임)을 결정하지 않는다.
- 기사 본문 크롤링 (저작권 — 원문 링크로 연결)
- LLM 기반 구조화 추출 (§13 확장 계획)
- 기사와 `companies` 테이블 매칭 (§13)

### 설계 원칙
1. **뉴스 기능 실패가 기존 기능을 망가뜨리지 않는다.** 모든 통합 지점에서 격리.
2. **불확실한 데이터는 버리지 말고 `null`로 둔다.** 라운드·금액·언론사 추출 실패가 저장 실패가 되면 안 된다.
3. **홈 화면 TTFB를 늘리지 않는다.** 현재 홈이 이미 느린 상태(약 4초)이므로 뉴스 쿼리는 반드시 캐시된 경로로만 접근한다.

## 3. 외부 API 명세

### 네이버 검색 API — 뉴스

| 항목 | 값 |
|---|---|
| Endpoint | `GET https://openapi.naver.com/v1/search/news.json` |
| 인증 헤더 | `X-Naver-Client-Id`, `X-Naver-Client-Secret` |
| 비용 | 무료 |
| 한도 | 일 25,000회로 알려져 있으나 **C4에서 재확인** |

**요청 파라미터**

| 파라미터 | 설명 | 사용값 |
|---|---|---|
| `query` | 검색어. **UTF-8 URL 인코딩 필수** (`URLSearchParams` 사용) | §4 키워드 |
| `display` | 한 번에 받을 개수 (최대 100) | `100` |
| `start` | 시작 위치 (최대 1000) | `1` (페이징 시 101, 201…) |
| `sort` | `sim`(정확도) / `date`(최신순) | `date` |

**응답 필드 (`items[]`)**

| 필드 | 설명 | 주의 |
|---|---|---|
| `title` | 제목 | `<b>` 태그 + HTML 엔티티(`&quot;` `&amp;` `&lt;` `&gt;` `&#39;` `&apos;`) 포함 → 제거·디코딩 필수 |
| `originallink` | 언론사 원문 URL | **빈 문자열일 수 있음** |
| `link` | 네이버 뉴스 URL | 미제휴 매체는 `originallink`와 동일 |
| `description` | 요약문 | `title`과 동일 처리 |
| `pubDate` | RFC 1123 (예: `Mon, 14 Sep 2026 09:00:00 +0900`) | `new Date()` 파싱 후 `.toISOString()` 저장 |

응답 메타: `total`, `start`, `display`.

> **본문은 제공되지 않는다.** 제목 + 요약만으로 모든 판정을 해야 한다.

### 에러 처리

| 상태 | 처리 |
|---|---|
| 400 | 파라미터 오류 → throw, 재시도 금지 |
| 401 / 403 | 키 오류 → 즉시 throw, 재시도 금지, 전체 동기화 중단 |
| 429 | 한도 초과 → **남은 키워드 전부 건너뛰고** `sync_logs`에 `status: "partial"` 기록 |
| 5xx / 네트워크 오류 | 최대 2회 재시도 (1초, 3초 백오프) |
| 타임아웃 | `AbortController`로 10초 제한 |

## 4. 수집 키워드

```ts
// src/lib/naver/constants.ts
export const NEWS_KEYWORDS = [
  "시드 투자 유치",
  "프리A 투자",
  "시리즈A 투자 유치",
  "시리즈B 투자 유치",
  "시리즈C 투자 유치",
  "스타트업 투자 유치",
  "벤처투자 유치",
  "스타트업 인수합병",
  "스타트업 정부지원사업",
] as const;
```

- 키워드당 1회 호출 → 실행당 9회. 호출 사이 `delay(100)`.
- 한 기사가 여러 키워드에 걸릴 수 있다. `keyword` 컬럼에는 **처음 수집한 키워드 하나만** 저장한다(중복 제거가 뒤따르므로 나중 것은 버려진다). 이 값은 어떤 키워드가 잘 작동하는지 분석하는 용도이며, 정확한 귀속을 보장하지 않는다.
- 페이징은 기본 사용하지 않는다. `sort=date`로 최신 100건이면 하루치로 충분하다. `total`이 100을 넘고 가장 오래된 기사가 `sinceDays` 범위 안이면 그때만 다음 100건을 요청한다(최대 3페이지=300건에서 중단).

## 5. 필터링

모든 판정은 **HTML 정리를 마친** `제목 + " " + 요약` 문자열 기준.

### 5-1. 전처리
1. `<b>`, `</b>` 등 모든 태그 제거
2. HTML 엔티티 디코딩
3. 연속 공백 1칸으로 축소, 앞뒤 trim

### 5-2. 날짜 컷오프
`pubDate`가 `sinceDays` 범위 밖이면 버린다. `sinceDays` 정의는 §7-2 참조.

### 5-3. 제외 규칙 (하나라도 걸리면 버림)
- 증권 홍보성: `상한가`, `급등`, `급락`, `테마주`, `수혜주`, `추천주`, `리딩방`, `급등주`
- 광고성: `무료체험`, `이벤트 당첨`, `할인 쿠폰`, `제휴 문의`
- 해외 단독: `뉴욕증시`, `나스닥`, `S&P` 포함 + 한글 기업명 패턴 없음

### 5-4. 관련성 점수 (2점 이상 통과)

| 조건 | 점수 |
|---|---|
| 투자 라운드 단어 (`시드`, `프리A`, `시리즈A~D`, `Pre-IPO`, `프리IPO`) | +2 |
| 금액 표현 (`\d+억`, `\d+조`, `\d+만 달러`) | +1 |
| 투자 행위 (`유치`, `투자`, `라운드`, `밸류에이션`, `펀딩`) | +1 |
| `스타트업`, `벤처`, `액셀러레이터`, `VC`, `창업` | +1 |

> 이 기준은 **초기값이다.** 최초 수집 50~100건을 육안 확인한 뒤 조정한다. 조정 근거를 이 문서에 기록할 것.

### 5-5. 라운드·금액 태깅 (실패해도 저장)
- `round_name`: `src/types/funding.ts`의 `ROUND_NAME_LIST` 값 중 매칭되는 것. 실패 시 `null`.
- `amount_text`: 매칭된 **원문 문자열 그대로** (예: `"50억원"`). 숫자 변환하지 않는다 — 단위가 섞여 있어 파싱 실패 시 데이터가 오염된다.

## 6. 중복 제거 ★ v1에서 가장 결함이 컸던 부분

투자 소식은 보도자료 하나를 수십 매체가 동시에 내보내므로 중복률이 매우 높다. **3단계로 처리한다.**

### 6-1. URL 중복 (완전 일치)
`originallink`가 비어 있으면 `link` 사용. 아래 순서로 정규화 후 SHA-256 → `url_hash`.
1. 프로토콜을 `https`로 통일, 호스트 소문자화, `www.` 제거
2. 트래킹 파라미터 제거: `utm_*`, `fbclid`, `gclid`, `ref`, `from`
3. 끝의 `/` 제거

### 6-2. 내용 중복 (핵심) — `content_key`
v1의 "제목 해시 완전 일치" 방식은 **작동하지 않는다.** 재작성 기사는 제목이 미묘하게 달라 해시가 갈린다. 대신 제목에서 **의미 요소만 뽑아 키를 만든다.**

```
content_key = `${기업명추정}|${round_name ?? "-"}|${금액숫자 ?? "-"}`
```

- **기업명 추정**: 정리된 제목에서 첫 번째 조사(`은/는/이/가/,`) 앞의 명사구, 또는 `[대괄호]` 제거 후 첫 어절. 추정 실패 시 제목에서 공백·특수문자·숫자를 모두 제거한 문자열의 앞 20자를 사용.
- **금액숫자**: `amount_text`에서 숫자와 단위만 추출해 정규화 (`"50억원"` → `50억`).
- 예: `"A사, 50억 시리즈A 유치"`와 `"A사 시리즈A 투자 50억원 유치"` → 둘 다 `A사|Series A|50억`으로 같은 키.

같은 `content_key`가 **최근 7일 내에 이미 있으면 저장하지 않는다.**

**조회 방식 — 건건이 쿼리하지 말 것.** 기사 수백 건을 하나씩 조회하면 N+1이 되어 실행 시간이 폭증한다. 실행 시작 시 아래처럼 **한 번만** 가져와 메모리 `Set`에 담고, 이후 판정은 메모리에서 한다.

```ts
const { data: existing } = await supabase
  .from("startup_news")
  .select("url_hash, content_key")
  .gte("published_at", sinceIso);

const seenUrlHashes = new Set(existing?.map(r => r.url_hash) ?? []);
const seenContentKeys = new Set(existing?.map(r => r.content_key) ?? []);
```

> Supabase는 기본적으로 한 번에 최대 1,000행만 반환한다. 7일치가 1,000건을 넘으면 중복 판정에 구멍이 생기므로, `existing.length`가 1,000이면 `.range()`로 페이징해 전부 가져와야 한다. **이 프로젝트의 대시보드 통계 쿼리에도 같은 문제가 있으니 함께 점검할 것.**

> 기업명 추정은 정확도가 완벽하지 않다. 이 키는 **중복 제거 용도로만** 쓰고, 화면 표시나 기업 매칭에는 절대 사용하지 않는다.

### 6-3. 실행 내 중복 (v1 누락)
DB 조회만으로는 **같은 실행에서 9개 키워드가 가져온 동일 기사를 못 거른다.** 실행 시작 시 `Set<string>` 두 개(`seenUrlHashes`, `seenContentKeys`)를 만들어 처리한 항목을 누적하고, 매 항목마다 DB 조회 **전에** 먼저 확인한다.

### 6-4. DB 저장 시 충돌 처리 (v1 누락)
`url_hash`에 UNIQUE 제약이 있으므로 일반 insert는 중복 시 에러가 난다.

```ts
const { data, error } = await supabase
  .from("startup_news")
  .upsert(rows, { onConflict: "url_hash", ignoreDuplicates: true })
  .select("id");

const insertedCount = data?.length ?? 0;  // 실제 저장된 건수
```

- 배치 크기 100건으로 나눠 저장한다.
- `inserted` 카운트는 반드시 `.select()` 반환 행 수로 센다. 입력 배열 길이로 세면 틀린다.

## 7. 동기화 실행 규칙

### 7-1. 마지막 성공 시각 기준 수집 (v1 누락)
크론이 하루 실패하면 그날 기사가 영영 들어오지 않는 문제를 막는다.

1. `sync_logs`에서 `sync_type = "news_cron"` 이고 `status IN ('success','partial')` 인 **가장 최근** 행의 `started_at`을 조회
2. 없으면(최초 실행) 기본값 사용
3. 있으면 그 시각으로부터 지금까지를 수집 범위로 한다

### 7-2. `sinceDays` 정의
- **최초 실행**: 7일
- **이후 실행**: `max(2, 마지막 성공 이후 경과 일수 + 1)`
- 최대 30일로 상한 (오래 실패했을 때 폭주 방지)
- **+1일 여유를 두는 이유**: Vercel Hobby 크론은 지정 시각으로부터 최대 1시간 내 임의 시점에 실행되므로 실행 간격이 23~25시간으로 흔들린다. "정확히 24시간" 가정은 깨진다.

### 7-3. 멱등성
같은 시간 범위로 몇 번을 실행해도 `inserted`가 0이어야 한다(첫 실행 제외). §6의 3단계 중복 제거가 이를 보장한다.

## 8. 언론사 추출 (v1 누락 — API가 제공하지 않음)

네이버 API 응답에는 언론사명이 없다. `originallink` 도메인에서 유추한다.

```ts
// src/lib/naver/press.ts
```

## 9. DB 스키마

마이그레이션: `supabase/migrations/<YYYYMMDDHHMMSS>_startup_news.sql`
(기존 파일명 관례: `20260420161200_review_tables.sql`)

```sql
create table if not exists startup_news (
  id           uuid primary key default gen_random_uuid(),
  title        text        not null,
  description  text,
  url          text        not null,
  naver_url    text,
  press        text,
  published_at timestamptz not null,
  keyword      text,
  round_name   text,
  amount_text  text,
  score        int         not null default 0,
  url_hash     text        not null unique,
  content_key  text        not null,
  created_at   timestamptz not null default now()
);

create index if not exists idx_startup_news_published_at
  on startup_news (published_at desc);

-- content_key 중복 조회는 항상 "최근 N일 내"로 걸리므로 복합 인덱스
create index if not exists idx_startup_news_content_key
  on startup_news (content_key, published_at desc);

-- 보관 정책 배치용
create index if not exists idx_startup_news_created_at
  on startup_news (created_at);

alter table startup_news enable row level security;

-- 뉴스는 공개 데이터 → 익명 읽기 허용
create policy "startup_news_public_read"
  on startup_news for select
  to anon, authenticated
  using (true);

-- 쓰기 정책 없음 = service_role만 가능 (service_role은 RLS 우회)
```

### 데이터 보관 정책 (v1 누락)
- 크론 실행 시 `published_at < now() - interval '180 days'` 인 행을 삭제한다.
- 1회 실행당 최대 1,000행까지만 삭제(긴 트랜잭션 방지). 남으면 다음 실행에서 계속 지워진다.
- 삭제 건수를 `sync_logs.summary`에 포함한다.

### `getRecentNews` 규칙
- 기본 `limit` 10, 최대 50으로 clamp.
- 정렬: `published_at desc`.
- **UI를 모르는 상태이므로 날짜 포맷·금액 변환·텍스트 자르기를 하지 않는다.** DB 값을 그대로 매핑해 반환한다.
- **`cookies()`를 쓰는 서버 Supabase 클라이언트를 사용하지 않는다.** 공개 데이터이므로 anon key로 만든 캐시 가능한 클라이언트를 쓴다(§12-1).

### `GET /api/news` 계약 (v1 누락)

**쿼리 파라미터**

| 이름 | 타입 | 기본 | 검증 |
|---|---|---|---|
| `limit` | number | 10 | 1~50, 벗어나면 clamp |
| `cursor` | string (ISO 8601) | 없음 | 파싱 실패 시 400 |
| `round` | string | 없음 | `ROUND_NAME_LIST`에 없으면 400 |

**응답 200**
```json
{
  "items": [ /* StartupNews[] */ ],
  "nextCursor": "2026-09-10T02:00:00.000Z"
}
```
- 커서 페이지네이션: `published_at < cursor` 조건. 더 없으면 `nextCursor: null`.
- **offset 페이지네이션을 쓰지 않는다** — 새 기사가 들어오면 페이지가 밀린다.

**응답 400**: `{ "error": "잘못된 요청", "detail": "..." }`
**응답 500**: `{ "error": "조회 실패" }` — 내부 에러 메시지를 그대로 노출하지 않는다.

## 12. 성능·통합 ★ v1에서 누락된 핵심

### 12-1. 캐싱 (반드시 구현)
홈 화면 TTFB가 이미 약 4초다. 캐시 없이 쿼리를 추가하면 상황이 악화된다.

- 뉴스는 하루 한 번만 갱신되므로 **정적 캐시 + 크론 후 무효화** 조합을 쓴다.
- 홈 페이지(`src/app/page.tsx`)에 `export const revalidate = 3600;`
- 크론 동기화 완료 후 `revalidatePath("/")` 호출.
- `getRecentNews`는 쿠키를 읽지 않는 클라이언트를 써야 캐시가 동작한다. 쿠키를 읽는 순간 동적 렌더링으로 전환돼 캐시가 무력화된다.

### 12-2. 크론 통합 (C1/C2에 따라 분기)

**Vercel 크론 제약 (2026-09 문서 확인)**
- Hobby: 크론은 하루 1회만 실행 가능하고 지정 시각으로부터 **1시간 내 임의 시점**에 실행된다. UTC만 지원한다.
- 프로젝트당 크론 개수 제한은 자료마다 달라(Hobby 2개 / 전 플랜 100개) **C1에서 대시보드로 직접 확인할 것.**
- 함수가 최대 실행 시간을 넘으면 `504 FUNCTION_INVOCATION_TIMEOUT`이 나고 **작업이 중간에 잘린다.**

**분기 판단**
- 크론 슬롯이 남고(C1) 기존 DART 동기화가 이미 길다면(C2) → `/api/cron/news`로 **분리**한다. 기존 동기화가 뉴스 때문에 잘리는 것을 막는 게 우선이다.
- 슬롯이 없으면 → 기존 `/api/cron/sync` 끝에 이어 붙이되, 아래를 지킨다.

**공통 필수 사항**
```ts
export const maxDuration = 60;  // 플랜 한도 내에서 명시적으로 설정
```
- 뉴스 동기화는 **반드시 try/catch로 격리**한다. 실패해도 DART 결과를 정상 반환(200)하고 로그만 남긴다.
- `durationMs`를 측정해 로그에 남긴다. 한도의 70%를 넘기 시작하면 분리를 검토한다.

### 12-3. 로깅
`sync_logs`에 `sync_type: "news_cron"`(수동 실행은 `"news_manual"`)으로 별도 행 기록.
- 시작 시 `status: "running"` insert → 종료 시 update
- `status`: `success` / `partial`(429 등으로 일부만) / `failed`
- `summary` 예시: `수집 312 / 통과 47 / 중복 29 / 저장 18 / 삭제 0 / 4.2s`

### 12-4. 수동 실행 라우트 인증 ★ 기존 코드의 결함 주의

기존 `src/app/api/cron/sync/route.ts`의 인증 함수는 **`CRON_SECRET`과 `DART_SYNC_SECRET`이 둘 다 없으면 `true`를 반환한다**(개발 환경 편의용). 환경 변수 설정이 누락된 채 배포되면 누구나 동기화를 실행할 수 있다.

`/api/admin/sync-news`는 이 패턴을 복사하지 말고 아래를 지킨다.
- 시크릿이 설정되지 않았으면 **401을 반환한다** (통과시키지 않는다).
- 개발 환경 예외가 필요하면 `process.env.NODE_ENV === "development"` 조건을 명시적으로 확인한다.
- 기존 크론 라우트도 같은 방식으로 고치는 것을 권장한다(이번 작업 범위 밖이지만 기록해둠).

### 12-5. 조회 API 남용 방지
`/api/news`는 인증 없이 공개된다. Vercel 함수 비용이 발생하므로:
- `limit` 상한 50을 서버에서 강제
- 응답에 `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400` 헤더 설정
